# dsh-switchman 架构诊断与重构指导文档

## 0. 一句话判断

**dsh-switchman 的调度骨架方向是对的，但它的“调度锚点”放错了位置：它以“池/岗位”来组织子任务，而正确的锚点应该是“运行时约束 + 可组合技能”。** Agent Teams 不应是默认升级路径，Skills 也不应是三个捆绑工具的附属品——它们应当共同构成 switchman 的一级调度对象。


## 1. 现况诊断：它是什么，它做了什么

dsh-switchman 不是一个新模型，而是挂在 DeepSeek Harness 上的**调度 doctrine + 设置页**。安装后，主模型从“自己干活”转为“测量水位、选车道、派活、验收”。

它目前做八件事：

1. **上下文水位线**：80k soft 提醒委派，100k hard 收紧读取预算，200k force 强制交接（写交接文档 → 压缩 → 唤醒续跑；append-only session log 本身就是完整备份，独立 fork 备份已于 2026-11-05 移除）。支持 `/ctx-pause` 临时接管和 `/ctx-handover` 手动提前交接。
2. **六个派发池**：economy / mechanical / main / hard / vision / review。每轮 prompt 注入 `[SWITCHMAN:POOLS]` 推荐表，执行模式 off / advice / enforce。
3. **Agent Teams 模式**：`teamsMode` 默认开启，注入团队 doctrine（delegate-by-default + 分级验证 + 共享任务板），主模型可以 `spawn_teammate`、使用 `team_task_*`、给队友发消息。
4. **语言偏好**：回复 / 代码注释 / 文档各一个下拉，问一次记住。
5. **界面语言**：插件自身 UI 跟随或手动选择语言。
6. **分级验证**：改动 >20 行走 tester，>300 行或触及核心/安全/数据一致性逻辑额外走独立 reviewer；review 模型锚定在“写 diff 的 agent”所用的模型上，尽量避开它。
7. **`/vision`**：主模型不支持图片时，把图片派给 vision 池模型，结论回注当前会话。
8. **意图路由**：Auto 模式下小分类器逐条决定交给谁，置信度不足或缓存窗口内不切换，护住 prompt 缓存。
除这八件主轴之事，仓库里还有若干守护性机制：工具参数透明矫正、PTC 直调 guard、自动 fold 管线、HMR 事务重试、四个出厂预设补丁与 UI 徽标。它们不改变调度主轴，本文只在相关处提及。

**已经做得好的地方**：水位线干预、任务分流、交接时保留后台 subagent 的 id 和报告路径、fold 的 append-only 缓存契约（“每次 fold 重付一次前缀，目标是摊销而非满分命中率”）。这些在之前讨论中已经确认方向正确。


## 2. 深层矛盾：三个尚未被正面回答的问题

### 2.1 锚点错位：用“岗位”调度，而不是用“约束”调度

六个池的本质是**成本/能力等级**的划分，而不是**任务约束**的划分。一个任务被派到 `economy` 池，是因为它“轻”，还是因为它“只需要读文件、不需要视觉、不需要独立验证、没有跨权限边界”？这两者在当前架构中是混在一起的。

小红书文章和评论区反复指向同一个结论：**拆分的依据应该是具体的系统约束，而不是岗位分工**。用一个 Agent 派发多个 subagent、给不同 subagent 设置不同模型，就能解决“不同任务配不同模型”的问题，不需要维护一个按角色划分的 team。Agent Teams 的常驻队友 + 共享任务板恰恰制造了成员之间的持续上下文耦合，这正是文章批评的形态。

当前 `teamsMode` 开启后注入的“delegate-by-default doctrine”更是把这个方向推得更远：它把“派活”变成了默认姿态，而不是“遇到约束瓶颈再派活”。

### 2.2 Skills 的边缘化：三个捆绑工具，而不是一级调度对象

switchman 捆绑了三个 skills：`db-query`（只读 MySQL/Redis 验证）、`git-commit-message`（生成 commit 文本）、`requirement-docs`（需求/PRD/设计文档归档）。它们作为“附带工具”存在，而不是调度决策的候选对象。

Claude Code 的 Skills 机制展示了另一种可能：**渐进式披露**。每个 skill 的元数据（名称 + 一句话描述，约 100 tokens）始终在上下文中，SKILL.md 主体（建议 <5,000 tokens）只在模型决定调用时加载，捆绑的脚本和资源仅在真正需要时读取。这意味着元数据目录的常驻成本是**线性可控**的——每条约 100 tokens，但上百个 skill 累计可达数千 tokens，在 80k soft 水位下并非“可以忽略”，需要按作用域挂载并设目录上限；模型按“当前任务匹配哪个简介”自主拉取完整流程。

Switchman 目前把“能力”主要放在**池的候选模型**和**三个捆绑 skill** 里。但真正的可组合能力——比如“如何做一次数据库迁移验证”“如何写一个符合团队规范的 API 变更”“如何跑一套端到端回归”——更适合被封装成 skill，由主模型在识别到约束时**按需拉起**，而不是预先分配到一个池里。

### 2.3 水位线是静态的，成本模型没有进入决策回路

80k / 100k / 200k 是固定阶梯，行为可预测，但对“上下文变重速度”不敏感。快速膨胀的高密度工具调用会话和缓慢增长的普通对话在同一个 200k 触发，前者的边际成本可能早已不划算。

更重要的是，**缓存命中价 0.02 元/百万、未命中 1 元/百万的 1:50 比例**，意味着“继续聊”的输入成本极低，而一次折叠/交接要按未命中价重付压缩后上下文 + 摘要输出成本。量级上：在 200k 水位继续聊，每轮缓存命中输入成本只有约 0.004 元；而一次交接的一次性重付（示例假设：压缩到 100k、按未命中价计）约 0.1 元，只相当于 25 轮左右继续聊的输入成本。这个比例说明：**纯输入成本公式几乎不会先于固定阈值触发**，“继续”的真正主导成本是空闲超过缓存 TTL 后的整段未命中重付，以及高 reasoning 档的输出 token 成本。当前架构没有把“本轮继续的预估成本 vs 交接的摊销成本”放进触发条件里，水位线只是一个 token 计数器。


## 3. 核心判断：架构需要调整，但不是推翻

需要调整的层面：

| 层级 | 现况 | 调整方向 |
|---|---|---|
| **编排哲学** | 池/岗位驱动，Agent Teams 是默认开启的常驻模式 | 约束驱动，Skills + subagent 是一级调度对象，Agent Teams 降级为例外 |
| **能力组织** | 六个池的模型候选 + 三个捆绑 skill | Skills 成为可组合能力单元，按约束标签匹配 |
| **水位线** | 固定 80k/100k/200k | 固定阈值兜底 + 成本敏感动态提前量 |
| **调度反馈** | 开环推荐表，池配置手动 | pool × skill × model 滑动窗口统计，推荐表带反馈 |
| **交接开销** | 同步文档 + 压缩 | 最小同步 handoff + 异步完整画像 + 按池预算压缩 |

不需要调整的层面：零运行时依赖的硬性不变量、fold 的 append-only 缓存契约、fail-open 回退原始历史的稳健性设计。


## 4. 重构方案：以“约束 + Skills”为锚点的调度架构

### 4.1 分层模型

重构后的 switchman 应被理解为三层：

**第一层：约束识别层。** 每轮请求在派发之前，先识别当前任务触及哪些**运行时约束**。约束不是“岗位名称”，而是一组可判定的条件：

- `context_pressure`：水位是否接近需要干预的区间
- `verification_required`：改动是否触及核心/安全/数据一致性，或超过行为阈值
- `capability_gap`：当前主模型缺少某能力（视觉、长上下文、特定工具链）
- `parallelizable`：子任务之间是否真正独立
- `permission_boundary`：是否需要跨信任边界调用
- `skill_match`：当前任务是否匹配某个已安装 skill 的描述元数据

约束识别可以由现有意图分类器扩展（它本身是一次要求严格 JSON 输出、带置信度与缓存窗口的 LLM 辅助请求），不需要新模型。但要写明各约束的**输入与判定方式**，否则第二层不可实现：`context_pressure` 与行为阈值（行数、改动规模）是确定性信号，直接读水位计数器与 diff 统计，不走分类器；`capability_gap`、`parallelizable` 由分类器结合会话状态给出弱信号；`verification_required` 中“触及核心/安全/数据一致性”无法可靠自动判定，只能由主模型在任务分解时自评（doctrine 引导，advisory 性质）。识别器不读取 diff 全文、不增加额外串行 LLM 调用，每轮注入成本以一条短标签行为限。

**第二层：调度决策层。** 约束命中后，选择**动作**，而不是直接选“池”：

- 命中 `skill_match` → **加载对应 skill**（渐进式披露：先只有元数据，决策后才加载 SKILL.md）
- 命中 `capability_gap` → **按能力标签派 subagent 到对应模型**（vision / long-context / 特定工具权限）
- 命中 `verification_required` → **无状态 review subagent 一次性调用**，不进入常驻 team
- 命中 `parallelizable` 且子任务真正独立 → **subagent 并行派发**
- 只有跨信任边界对接独立系统时，才考虑 A2A
- `context_pressure` 触发水位线动作（见 4.3）

池仍然存在，但**池从“调度单位”降为“模型候选集合”**：约束识别决定“要不要派、派什么类型的活”，池只回答“这个类型的活，当前哪些模型可用、优先级如何”。

**第三层：反馈与观测层。** 每个 `约束 → 动作 → 结果` 被记录，形成滑动窗口统计，回注推荐表。

### 4.2 Skills 作为一级调度对象

**将捆绑 skills 从“附带工具”提升为调度候选**，并开放 skill 注册机制。

每个 skill 的 frontmatter 包含：

- `name`：技能名
- `description`：一句话描述（始终在上下文的元数据，约 100 tokens）
- `constraints`：该 skill 适用的约束标签（如 `db-write-verification`、`api-breaking-change`、`regression-suite`）
- `estimated_tokens`：SKILL.md 主体的预估大小（注册时自动测量生成，不由作者手工维护）
- `pool_hint`（可选）：建议的执行模型能力等级

主模型每轮看到的是 **skill 元数据目录**（“名称 + 一句话 + 约束标签”），而不是完整内容。当约束识别命中某个 skill 的标签，或主模型判断当前任务匹配某个 skill 描述时，才加载 SKILL.md 主体。
**与宿主原生 skill 目录的关系**：DSH 宿主本身已注入 available_skills 元数据并按需加载 SKILL.md——渐进式披露是宿主能力，switchman 的三个捆绑 skill 正是经运行时 `ctx.skills` provider 注册进去的。因此 switchman 不应另建一套平行元数据目录，而应做**注解层**：为 skill 补充 `constraints` / `pool_hint` 标签；`[SWITCHMAN:SKILLS]` 只注入带约束注解的增量行与宿主目录之外的本地 skill，避免同一 skill 出现两份元数据、两套触发条件。

**这样做的直接收益**：switchman 不再需要为每一种“活儿”预定义一个池。`economy` 池和 `mechanical` 池的很多场景，本质上是在做“没有对应 skill 时的默认兜底”。有了按约束匹配的 skill 系统，池的粒度可以变粗，skill 承担“具体怎么做”的知识，subagent 承担“隔离执行”的边界。

### 4.3 水位线：固定兜底 + 成本敏感动态触发

保留 80k / 100k / 200k 作为**上限兜底**（行为可预测，关闭 dynamic 时完全兼容旧版），在固定阈值之下增加动态提前量。

动态提前量取两个信号：**增长率为主、成本为次**。

**增长率信号（主）**：令 `growth_rate` ≈ 近 k 轮上下文净增 tokens / k（工具输出 + 模型输出 − fold 抵扣）。当 `当前水位 + growth_rate × N_expected` 外推会撞到 hard / force 阈值时，提前进入对应干预档位。它直接回应 2.3 的“变重速度”问题，不依赖价格参数，也不会被缓存命中低价稀释。

**成本信号（次）**：对比必须是**增量式**的——交接后继续并非零成本，每轮仍要按压缩后水位付命中输入与输出：

- `C_stay(n)` ≈ Σᵢ (当前水位 + i·growth_rate) × 命中价 + n × 单轮输出成本
- `C_switch(n)` ≈ C_handoff + Σᵢ (压缩后水位 + i·growth_rate) × 命中价 + n × 单轮输出成本，其中 `C_handoff` ≈ 压缩后上下文 × 未命中价 + 摘要输出成本
- `N_expected`：用户配置或按近期轮距估算

当 `C_stay(N_expected) > C_switch(N_expected) × amortization_factor`（默认 1.5～2，作为对估计误差的保守垫）时提前交接，但**不晚于固定 force 阈值**。两点现实修正：① 在 1:50 的价格比下，纯输入成本项要 `N_expected` 达数十轮量级才为正（见 2.3 的量级示例），所以成本信号的真实作用是决定 soft 档要不要提前收敛读取预算，而不是替代 force；② “继续”的主导成本是空闲超过缓存 TTL 后的整段未命中重付与高 reasoning 档的输出成本，前者可结合近期轮距估计 miss 概率（与 P2 的缓存窗口自适应衔接），后者按档位系数计入输出项。

价格与窗口参数通过配置注入，不硬编码。日志记录触发原因 `fixed_force` / `dynamic_growth` / `dynamic_cost` / `manual`。

### 4.4 Agent Teams 的重新定位

Agent Teams 不应被删除，但**默认路径必须是“无状态 subagent + 按需 skill”**。

具体调整：

1. **`teamsMode` 从“默认开启的手动开关”改为“约束触发的建议”，默认值收紧为关闭**。只有当约束识别同时命中多个条件（真正的并行独立子任务 + 需要隔离权限 + 需要持续性协作）时，才**建议**进入 Agent Teams，而不是默认注入 delegate-by-default doctrine。
2. **常驻 teammate 的创建增加显式理由要求**。`spawn_teammate` 之前要求主模型声明触发了哪条约束；没有理由的常驻队友被拒绝或标记为 advisory。该要求第一版是 doctrine 层软约束，不做工具层硬拦截——硬校验需要 hook 工具调用、且易被敷衍声明绕过，复杂度与收益不成比例。
3. **review 角色保持无状态、隔离上下文**。验证的价值来自独立性，不是来自“坐在同一个 team 里”。review subagent 一次性调用，不进入共享任务板。
4. **共享任务板的默认作用域收窄**。任务板只服务于已经明确进入 Agent Teams 的会话，不向普通 subagent 派发渗透。

### 4.5 池的反馈闭环

现有六个池的候选模型、优先级、S/A/B/C 等级、思考强度全部手动配置，属于开环调度。引入轻量滑动窗口统计：

记录每个 `pool × model × skill（如有）` 组合的**成功率、平均延迟、重试/返工率**。将统计注入 `[SWITCHMAN:POOLS]` 推荐表，例如：

```
economy: modelA(success=0.97, latency=1.2s), modelB(success=0.91, ...)
```
成败信号分两档：**进程性信号**（子智能体异常返回、超时、空结果）直接可观测，入统计；**返工信号**第一版只统计“同一目标在 k 轮内被重复派发到同一池”，不做语义级返工判断——后者噪声大且需要额外 LLM 判定，留待 P2。

可选自动降级：成功率低于阈值且样本量足够时，优先级下调一档，但**默认只影响推荐顺序，不硬禁用模型**。最小样本量不足时不调整。

### 4.6 交接开销的收敛

交接序列 `写交接文档 → 压缩 → 唤醒` 中，文档生成和压缩存在同步开销。

调整为：

- **`handoff_min` 同步生成**：任务目标、当前状态、下一步、关键文件/命令、后台 subagent 的 id 和报告路径。保证续跑立即可用。
- **`handoff_full` 异步生成**：成本画像、历史决策、未决问题。失败不阻塞续跑。
- **按 pool / skill 的目标预算反向约束压缩力度**：`target_after_compress = min(pool_target, current_context × compress_budget_ratio)`，避免一刀切压缩后仍然偏大、导致下一次交接更快到来。
- **备份来源已收敛**：独立 fork 备份已于 2026-11-05 移除，append-only session log 本身就是完整备份；本项剩下的是保持交接文档对 log 内 live-subagent id 与 catalog/record 路径的引用一致。


## 5. 实施路线图

### 第一阶段：锚点校正（P0，不改核心调度逻辑）

1. **约束识别层落地**：在现有意图分类器旁增加约束标签识别，输出 `constraints` 集合，先只用于日志和推荐表注入，不改变现有派发行为。
2. **Skill 元数据目录**：三个捆绑 skill 的 frontmatter 目前只有 name + description（db-query 另有 compatibility），补全 `constraints`（`estimated_tokens` 由注册时自动测量），并以 4.2 的注解层模式在 `[SWITCHMAN:POOLS]` 旁边注入 `[SWITCHMAN:SKILLS]` 增量表（每条约 100 tokens，无注解的 skill 不注入）。
3. **动态水位线估算器**：增加增长率外推与成本估算函数和配置开关，默认关闭；开启后动态触发只能提前、不能延后于固定 force；触发原因写入日志（`dynamic_growth` / `dynamic_cost`）。
4. **Agent Teams 的 doctrine 条件化**：`teamsMode` 开启时，delegate-by-default 改为“约束命中时才建议委派”，默认值随 4.4 收紧为关闭，保留“say don't use teams”立即退出的行为。

### 第二阶段：Skills 成为调度对象（P1）

1. **Skill 匹配与加载**：主模型可依据约束标签或 skill 描述，主动加载某个 skill 的 SKILL.md 主体；加载后记录 `skill_loaded` 事件。
2. **开放 skill 注册**：允许用户/团队按 frontmatter 规范注册新 skill，自动进入元数据目录。
3. **池反馈闭环**：开始记录 `pool × model × skill` 的滑动窗口统计，注入推荐表；自动降级默认关闭，仅输出建议。
4. **交接拆分**：`handoff_min` 同步、`handoff_full` 异步；按预算压缩。

**迁移与兼容约束**：任何池合并/改名必须保留旧池名别名，profile 内用户手动排序不丢失；新增 frontmatter 字段一律可选、缺省视为无注解；各阶段开关默认关闭或 advice，行为变化可在单会话内回退。

### 第三阶段：自适应与观测（P2）

1. **成本归因画像**：按 pool / skill / model / 类型（工具输出、模型输出、未命中尖峰）打标签，写入 `handoff_full`，续跑首轮注入简短提示。
2. **分池/分 skill 的切换置信度与思考强度差异化**。
3. **缓存窗口自适应**：基于实际消息间隔的 P90 调整缓存保护窗口（仍夹在厂商缓存窗口的安全边界内）。

**各阶段验收信号**：P0——约束标签进入日志与推荐表注入，且开/关对照下派发行为零差异；P1——`skill_loaded` 事件可查、推荐表出现统计数据、`handoff_min` 单独足以支撑续跑；P2——成本归因画像落盘、缓存窗口调整有 P90 依据。

## 6. 风险与边界

| 风险 | 缓解 |
|---|---|
| 约束识别误判导致错误派发 | 约束识别第一版只做**建议**，不改变强制路径；用户可关闭 |
| Skills 过多导致元数据膨胀 | 元数据每条约 100 tokens；按项目/作用域挂载，不全局灌入 |
| 动态水位线估算偏差 | 价格配置注入；默认关闭；动态只能提前不能延后；固定阈值兜底 |
| Agent Teams 条件化后“该建 team 时没建” | 保留手动 `/team` 覆盖；约束条件宁可宽松，不可漏掉真正的并行独立场景 |
| 自动降级误伤 | 最小样本量 + 仅影响推荐顺序 + 默认关闭 |
| 异步 handoff 滞后 | `handoff_min` 同步保证可用；异步失败 fail-open |
| Skill 元数据与宿主原生目录重复 | 注解层模式：不另建目录，`[SWITCHMAN:SKILLS]` 只注入增量行 |
| 约束识别的每轮开销与自评敷衍 | 确定性信号优先；主模型自评仅 advisory；标签行注入成本设上限 |
| 价格 / 窗口配置漂移 | 参数带版本化默认值；触发原因入日志，异常触发可审计回滚 |
| 用户在预设编辑器保存后 patch 层整体替换 `config.plugins`，注入的 persona suffix / doctrine 被丢弃 | 已知坑文档化；后续在注入点做 presence 校验，复用 HMR 挂起重试模式重新注入 |
**不动的边界**：零运行时依赖；fold 的 append-only 缓存契约；fail-open 回退原始历史。


## 7. 总结

dsh-switchman 不缺功能，缺的是一个**一致的调度锚点**。它目前用“池/岗位”来组织一切，导致 Agent Teams 被当作默认升级路径，Skills 被当作附属工具，水位线只是一个静态计数器。

重构的核心不是增加更多池或更多开关，而是**把“约束”和“技能”提升为一等公民**：约束识别决定动作，Skills 提供可组合的能力，池退为模型候选集合，Agent Teams 退为约束触发的例外路径。在这个基础上，再把成本敏感动态水位线、反馈闭环和交接开销收敛叠加上去，才是一个既保留现有稳健骨架、又真正适应当前模型生态（Flash 的低缓存价、Skills 的渐进式披露、subagent 的按需隔离）的调度系统。
