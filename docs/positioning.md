# Positioning: dsh-switchman as the fold engine

> Strategy doc, revised 2026-11-06 (same-day revision of the first version). Pivot: **the fold engine stays in this repo.** `host/context-trim/` is promoted from "fallback to be demoted" to the sole folding engine — a self-developed, in-process equivalent of what bili does at the transport layer. bili is rejected as an attach form for dsh entirely.

## Why the revision

The first version's premise — "a plugin sits at neither the byte-flow point nor the history-store point, so folding must live in the host core" — is the zcode lesson (hooks-only, append-only). It does not hold for dsh: the in-process Cordis model plus the `'llm/stream'` waterfall hands this plugin the **request-construction point** (`packages/llm/llm/src/index.ts:75` in the dsh repo — hook signature, emitted at `:1180`; path verified 2026-11-06), and context-trim already splices deterministic folded views there. The engine this repo needs is not something to build in the host core; it is already ~80% here and it is the only subsystem with a test suite.

## The bili mechanism mapping (what exists, what's missing)

| bili mechanism | context-trim status | Gap |
|---|---|---|
| Injected self-fold tools (compress / decompress / search_context / acp_status) | `ctx_trim_fold` / `ctx_trim_status` advisory tools exist | Optional: align naming/semantics (fold / unfold / search); `acp_status` analog lives in the watermark |
| Range-level folding with a consumed-ranges ledger | Ledger exists, with **copy-on-write fork inheritance** (`host/context-trim/fork.js`) — stronger than bili | Keep and document as the differentiator |
| Prefix-stable incremental folding (cache protection) | Deterministic outbound view splicing via `'llm/stream'` | Add the discipline: folds append, never rewrite already-folded segments |
| Side-model summaries | Exists (120 s timeout, 400k-char material cap) | None |
| Usage / watermark integration | Meter duality (watermark reads trim's view, wire-truth gate) | **Invert** — trim becomes the single meter authority (see plan C) |
| Persistence at the history store | None (view-layer only; the session store keeps full history — which is exactly what makes unfold/search free) | Optional Stage 3: a dsh seam to materialize folds as store-level summary nodes |

Algorithm-level detail and per-mechanism borrow verdicts: see the appendix at the end of this doc.

### B. Retire the competitors (the real slim-down)

These existed because nothing folded context. The engine now does. Principle: **flip defaults to off, keep code as break-glass until the engine is proven in daily use.**

1. **Force-tier auto-handover + entry compression** (`context-watch.js` handover path, `handover-state.js`, parts of `subagents.js`, `/ctx-pause` `/ctx-resume` `/ctx-handover`) — the 150k treadmill should never trigger once trim folds at pressure 60%. Retire from the hot path; keep behind an off-by-default flag.
2. **Read-budget double gate** (`ACCOUNT_TOOLS`/`GATED_TOOLS`) — shrink from cap/deny to a soft advisory.
3. **Watermark banner** — from a four-tier anxiety machine (ok/soft/hard/force) to a truthful readout of the folded view. The estimation machinery underneath stays (it is the engine's trigger input).
4. **Compaction arbitration** (`cordis.patch.yml` `auto:false`) — keep, with a better justification: "the switchman fold engine owns folding" — not "plugin trim temporarily beats host compaction". See Stage 3 for how this eventually dissolves.
5. **client.js (7,023 lines, 41% of source)** — the largest single lever. Retired features' UI goes with them; then decide whether the hand-written settings page + 12 inline language dictionaries become schema-driven / externalized. Every feature retired in B.1–B.4 shrinks this file too.

### C. Unify the meter (integration core)

One estimator module; every consumer reads it — banner, intent window clamp (`host/config.js:213-220`), trim triggers, future policy exports. Today estimation is duplicated (watermark `~len/3.5`, trim's own estimator) and the dependency points the wrong way (watermark reads trim's view at `host/context-trim/index.js:85`). Invert it: trim is the meter authority; the watermark subscribes.

## The convergence path (how "整合上下文压缩" ends)

- **Stage 1 (now):** context-trim is the sole folder. Host compaction stays arbitrated off. bili never enters the dsh stack (it remains a zcode-only attach form, where there is no alternative).
- **Stage 2:** competitors retire (plan B), meter unifies (plan C), trim hardens: append-only fold discipline, ledger integrity tests, fold/unfold/search tool alignment.
- **Stage 3 (optional):** dsh gains one small seam — a way for trim's ledger to **materialize** folded ranges as session-store summary nodes. Splicing then becomes a cache for not-yet-materialized folds; the arbitration dissolves because trim *uses* host compaction as its persistence layer instead of suppressing it. Host and plugin converge without a rewrite of either.

## Appendix: the bili algorithm, verified (2026-11-06)

Sources: the npm package ships its own paper (`billion-context@0.1.212/paper/模型驱动的分层增量压缩-免训练多代上下文管理.md`, preprint v0.2, 2026-09-07, 390 lines) and the compiled kernel (`dist/agent/pi-native.js` — pipeline phase names verbatim at `:333`, nudge wording at `:132`). bili = acp-kernel (~10k lines TS, 550+ tests) + a philosophy prompt. Its one-line thesis: **the model writes the summaries; the library orchestrates everything else** — no training, the judgment lives in versioned, host-configurable prompt text ("the training-free alternative to SFT").

**Architecture: a 9-phase pure-function pipeline per turn** — assign-refs → sync-blocks → merge-blocks → prune → filter → hide-compress-calls → nudge-inject → emergency-truncate → render-refs — exposed as `processTurn(state, messages, config) → (state', rendered, effects)`. The host never rewrites history; a fold only *deactivates* suffix ranges in the rendered view. That is the same append-only fold discipline plan B / Stage 2 assigns trim — independently confirmed as the load-bearing design (it is why their cache-read ratio hits 94.2% at active cadence).

**Blocks**: `{blockId, tier 1/2/3, topic, summary, directMessageIds, effectiveMessageIds, directBlockIds, survivedCount, generation, active}`. `effectiveMessageIds` is *transitive* — lineage survives re-folding. Tier-2 re-distillation is a safety valve, not a routine path (3.5% of production blocks). Don't build tier-2 now; keep the ledger ready for it (transitive coverage on re-fold). Decompress reactivates sources; **decompress-to-file** writes full text to the filesystem instead of back into context — restore without disturbing the KV prefix. A capability worth adding to trim's unfold later.

**Trigger (demand-side)**: fold nudge fires when context > 0.45×window AND growth-since-last-fold > 50K, with an effective minimum request of 22.5K (45% of the gate — never force a fold smaller than worth summarizing). **trim's constants already match: `increment 50000` = the growth gate, `growth 22500` = the effective minimum, `emergency 95` = their 95% emergency path. The engine was calibrated against these numbers; the remaining divergence is `pressure 60` vs their 0.45×window floor.**

**Protected zones are enforced in the filter phase, not the prompt**: the fold tool calls themselves (they carry the summaries), the recent zone (hard floor ~5 messages / ~5K tokens), the last user message, and the first user message (task intent). Assistant messages skip reference-label injection (anti-echo). trim's `protectedTail 6` covers the recent zone; check first-user-message protection.

**Six interactive mechanisms — the borrowable core:**

1. **Throttled increment-only requests** — never demand a fold below the effective minimum. trim has this.
2. **Never disclose the fill percentage to the model.** A model told "you're at 20%" anchors on "looks healthy" and refuses to fold; with the number hidden, judgment roots in the task. ⚠ This conflicts with the watermark banner: the banner serves the human — keep percentages out of any *model-visible* trigger payload.
3. **The right to refuse.** Nudge framing, verbatim from the kernel (`pi-native.js:132`): "an efficiency nudge to compress early and keep context lean — not an overflow warning." Refusal is a quality valve, not a failure.
4. **Transient attention.** The source ranges are fully visible during the fold call and hidden immediately after (hide-compress-calls) — the summary is written under full attention and the scaffold leaves no residue in later turns.
5. **The recommendation list with true sizes.** The nudge lists foldable ranges with real token counts and tool/text composition — the interface between bookkeeping and judgment; without sizes, models pick scattered low-value ranges. Borrow directly into trim's trigger payload.
6. **Unique per-message refs (mNNNNN).** All addressing by reference; measurably helps long-context attention even when no fold ever runs.

**Summary craft (KEEP/DROP, with priority order)**: goals > decisions+rationale > artifacts > conclusions > lessons. Verbatim-KEEP: paths with line numbers, signatures and load-bearing lines, exact error strings, decisions *with* their reasons, exact values, goal evolution, message refs for later unfold. DROP: verbose logs post-extraction, repeated reads, dead-end exploration *keeping the lesson*, process leading to a conclusion. Borrow verbatim into the summarizer prompt.

**Restoration asymmetry (measured)**: at this model scale, models do not spontaneously use recovery tools — recovery happens only when instructed. Fold summaries must say *when to unfold what*; trim's `ctx_trim_fold`/`ctx_trim_status` descriptions should carry the same instruction.

**Experiment lessons** (their controlled runs): philosophy text + message labels alone — zero folds executed — reproduced 62% of the reread-reduction; the prompt is the product, not just the mechanism. Compression frequency is the dominant knob; aggressive gates win on repetitive loads, lose on phase-structured ones (default gates are the robust point — trim's conservative defaults are correct). And the engine-paced deterministic arm beat model-driven folding by 37% on repetitive loads — trim *is* the deterministic arm; its missing half is task-awareness in *what* gets folded, which is exactly what the recommendation-list and philosophy borrowings supply.

**The dsh attach already exists upstream** (`dist/agent/dsh-native.js`, `dsh.bundle.patch.yml`, `dsh-compaction-gate.js`): bili's own host-compaction arbitration does at runtime what `cordis.patch.yml` does statically — an `internal/config` hook recursively disables compaction rows nested inside agent presets that static patch layers cannot address by id, with a `globalThis.__BILI_DSH_COMPACTION_VERDICT__` switch and a hard rule that the gate must outlive bili's own kill-switch, else presets wait forever on a dead gate and session creation bricks (their #3662). Reference reading for Stage 3 arbitration design — not a reason to attach bili.

**Architecture fact, verified 2026-11-06 against billion-context@0.1.212**: the folding kernel does NOT live in the dsh process. `dsh-native.js` contains zero occurrences of `processTurn` (the 9-stage pipeline entry) — it is only the in-process face: compaction gate + React settings/context panels. The kernel sits in the `bili` launcher/proxy (`dist/index.js`, 14× `processTurn`): `bili dsh` (or `/acp`) starts a sidecar proxy, dsh binds to it over loopback HTTP, folding happens in the proxy process, and dsh's own session store keeps full history — the same sidecar shape as bili-on-zcode, just with a launcher, a gate, and a Web UI. Their own UI strings manage the inherent failure modes of this shape: unbound ("当前 dsh 进程未绑定 bili 代理"), stale proxy ("运行中的 bili 代理比已安装的配置文件旧" — plugin/proxy version skew is a designed-for state), remote access needing a server-side config edit. So bili-in-dsh is the most polished possible *external* attach; it does not occupy trim's position (in-process view-layer splice) and never will — in-process folding with store-level persistence is exactly the category they did not build for dsh.

**Not borrowed, and why**: the transport attach (proxy/agent mode) — trim is in-process, the stronger position; tier-3 — tier-2 is already rare in production; the kernel *as code* — dist ships 2.3MB minified bundles; the readable source is `github.com/ranxianglei/acp-kernel` (DESIGN.md, DESIGN-prompts.md, 550+ tests) for when a mechanism needs the implementation, not just the spec.
