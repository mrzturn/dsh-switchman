## なぜ必要か

DSHで長く作業していると、悩みが2つ出てくる。1つはセッションの肥大化。履歴がコンテキストを数十万トークンまで膨らませ、モデルは忘れ始め、遅くなり、高くつき、手動の /compact は細部を失う。もう1つは主力モデルが何でも自分でやること。ファイルを追い、テストを回し、データを突き合わせる——その大半は実は安いモデルに任せるべき仕事だ。

dsh-switchman は [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（DSH）のプラグインだ。入れると主モデルは「自分で作業する」役から運転指令へ変わる：水位を測り、レーンを選び、タスクを投げ、受け入れを確認する。新モデルではない。DSHに取り付けるディスパッチ規程と設定ページであり、8つのことを行う。

**1. コンテキスト水位：長いセッションを破裂させない。** 毎ターンリアルタイムでセッショントークンを数え、3本の水位線が段階的に締め上げる：80k（soft、調整可）は「そろそろ委譲を」、95k（hard）は1回の読み取り予算を引き締めて収束へ導き、150k（force）で自動引き継ぎ——引き継ぎドキュメントを書き（追加型のセッションログ自体が完全なバックアップ）、コンテキストを圧縮し、セッションを起こして継続する。タスクは切れない。引き継ぎの瞬間に走っているバックグラウンドのサブエージェントも失われない：id・タスク・レポートパスを引き継ぎドキュメントに書き込み、再開したセッションはどこでレポートを受け取るか分かっていて、同じ仕事を二度投げない。各サブエージェントは独立のハード上限を持ち、到達したら HANDOFF サマリを書いて退場する。自動介入が手に合わないときは、いつでも一時的に手動で引き取れる：`/ctx-pause` は水位の動作をすべて止める（計測は走り続け、末尾のリアルタイム水位線は paused に切り替わる、ただ手を出さなくなるだけ）、`/ctx-resume` でいつでも復帰。DSH を再起動しても介入は自動で戻る。一時的に手を離すだけで、恒久的なオフではない。`/ctx-handover` は水位が満ちるのを待たず、同じ引き継ぎを自分から起こす：引き継ぎドキュメントを書き、コンテキストを圧縮し、セッションを起こす（セッションはまずアイドル境界まで導かれるため、結果には数分かかることがある）。

**2. 6つのディスパッチプール：仕事に合ったモデルを。** economy（小口の雑務のバッチ）、mechanical（テンプレート化された書き換え）、main（日常のコーディング）、hard（難問推論と大規模リファクタリング）、vision（画像）、review（独立検証）。設定ページで候補にチェックを付け、優先順を決め、S/A/B/C のグレードを付け、さらにルートごとに思考強度をピン留めできる——強度のドロップダウンはそのモデルが実際に対応するレベルから立ち上がり、汎用の3段ではない。主モデルの毎ターンのプロンプトには必ず `[SWITCHMAN:POOLS]` 推薦表が載り、表に従って投げる。実行モードは3態：オフ / アドバイス / 強制（強制＝プール外のモデルは即拒否）。

**3. Agent Teams モード：単独作業からチーム運用へ。** 既定はオフで、インストール直後は軽量なサブエージェント運用。設定ページに独立したトグルが2つ：

- **エージェントチーム**——オンにするとチーム規程（デフォルト委譲＋段階的検証＋共有タスクボードの規律）を注入し、DSH の Agent Teams を自動で有効にする：主モデルは常駐のチームメイトを引く（`spawn_teammate`）、共有タスクボードに仕事を置く（`team_task_*`）、チームメイトとメッセージをやり取りする。チームを組むべき場面は規律で決まっている：並列化できる独立サブタスク、量が多く自己完結した作業、主コンテキストの水位が既に高い、役割の分離が必要——使い捨ての単発調査は引き続きサブエージェントへ。トグルを戻せばチーム条項は跡形なく消え、実行中のセッションからチームツールを引き上げることもない。
- **サブエージェントモデルのホワイトリスト同期**——DSH には「エージェントにサブエージェントのモデル選択を許可する」認可リストがある：プールで選んだのに認可されていないルートは、名指しでの発令が拒否される（チームモードでは ⚠ 表示）。このトグルを入れると、6プールの和集合がまるごとそのリストへ書き込まれる——switchman が唯一の情報源になり、二重管理は不要。リストは「新規セッション」単位のスナップショットで効き、同期はそれ以降に開いたセッションにだけ効く。

セッションヘッダーには即座に分かるフィードバックがある：⚡「自律チーム」バッジ、◇ 現在セッションの実際のモデル。自動引き継ぎの実行中は「引き継ぎ実行中 ・ 引き継ぎ文書の作成 / コンテキスト圧縮 / 後継の起動」のライブ表示が出る。

**4. 言語設定：一度聞けば、ずっと守る。** 返信・コードコメント・ドキュメントの3言語にそれぞれドロップダウンが1つ。スコープはグローバルまたはプロジェクト単位（`.switchman/lang.json`）。未設定のままでもよい——初回使用時に DSH インターフェースの言語で一度だけ尋ね、覚えれば以後すべてのセッションが守る。

**5. インターフェース言語：プラグイン自身もあなたの言葉で。** 設定ページ最上部の「インターフェース」領域にある「インターフェース言語」ドロップダウン（設定キー `uiLocale`）：自動（既定、DeepSeek Harness アプリの言語に追従）または内蔵のインターフェース言語から任意に選択——選択肢は常にその言語の原語名のまま、翻訳しない。切り替わるのはプラグイン自身のインターフェース（バッジ・ホームパネル・設定ページ）だけで、DSH アプリの言語は動かさない：選択はその場でプレビュー、再起動不要、保存後に記憶し次回起動時に復元、失敗時はすべてアプリの言語へフォールバックする。辞書はすべてプラグインバンドルに内蔵、ダウンロード不要。

**6. 段階的検証：直したら必ず検査する。** 20行超の変更は tester へ。300行超、またはコア / セキュリティ / データ整合性に触れる変更は、さらに reviewer の独立再審へ。再審モデルは「その diff を書いたエージェント」のモデルを錨に選び、極力避ける。プール内で避けきれない場合は、結論の中で DOWNGRADED と宣言される。「チームは使うな」の一言で即座に単独へ戻る。

**7. `/vision`：テキスト専用モデルでも画像を扱える。** 主力モデルが画像を読めないとき、DSH は画像付きメッセージを入口で拒否する。画像を貼って `/vision この画像のどこが悪い` と打てば、画像は vision プールのモデルへ渡され、結論は現在のセッションに戻る。入力欄の上には「現在のモデルは画像を読めません」の事前表示が出る。画像を直接送って拒否されたら、自動で `/vision` に書き換えて再送するので手直しは不要。vision プールが未設定ならコマンドは拒否し、設定への案内を出す。

**8. 意図ルーティング：最適なモデルを自動で選ぶ。** 設定ページに「意図認識」グループが増える：マスタートグル（既定オフ、有効化には分類器と候補が最低1つ必要）、分類器用の小型モデルルート（provider + model + 任意の effort。TypeSafe Jev 系の決定モデルも汎用対話モデルも使え、出力は寛容にパースされる）、分類器タイプの3択（auto / decision / chat）、独立した候補モデルリスト（各候補に provider + model + 任意の effort + 一行の能力説明）、キャッシュウィンドウ秒数（既定 300、ベンダーの prompt cache 約5分に合わせる）、切替信頼度しきい値（既定 80）、分類タイムアウト（既定 60000ms）、履歴メッセージ件数（既定 6）と文字数予算（既定 2400）、任意のフォールバックモデル。モデルセレクターの「Auto · Switchman」グループの下に「Auto」エントリが現れる（クライアントは「自動（意図認識）」とローカライズして表示）；選んでおくとユーザーメッセージごとに分類器が最適な候補を判定し、判断はそのターンの間固定される：信頼度が足りない、またはまだキャッシュウィンドウ内なら現在のモデルをそのまま使い（キャッシュを再利用）、信頼度が十分高い、または現在のモデルが候補にないときだけ切り替わる。切替は呼び出し層で静かに行われ、「モデルを切り替えました」のメッセージをセッションに差し込まない。入力欄の上には状態 chip（自動ルーティング中は現在のルーティング先モデルと最後の判断の信頼度を表示）。候補としきい値はいつでも設定ページで確認できる。

モデルが1つでも入れる価値はある——水位制御と段階的検証はモデルの数と無関係で、単一モデルの長いセッションも同じく恩恵を受ける。

## 同梱スキル

- **db-query**——MySQL / Redis の読み取り専用検証：SQL でデータを突き合わせ、キャッシュキー / TTL を調べ、クロスDBの整合性を検査する。書き込みは一切拒否。初回使用前に初期化が必要（下記）。
- **git-commit-message**——規約に沿ったコミットメッセージを生成する。テキストだけ出し、git を代行することはない。
- **requirement-docs**——要件分析 / PRD / 設計ドキュメントの統一規程。成果物は `docs/requirements-and-design/` にアーカイブする。

## クイックスタート

1. **インストール**——任意のセッションで agent に実行させるか、Web のプラグイン管理ページで：

   ```
   plugin_manager: install_bundle  target=dsh-switchman
   ```

   またはローカルのチェックアウトから（link 方式。更新後は `remove_bundle` + `install_bundle` で入れ直す）：

   ```
   plugin_manager: install_bundle  target=/path/to/dsh-switchman
   ```

   または端末で `dsh` コマンドを——実行方法に合う profile を選ぶ：

   ```bash
   dsh plugin --profile web add dsh-switchman      # Web GUI
   dsh plugin --profile desktop add dsh-switchman   # デスクトップアプリ
   ```

2. **DSH を再起動**——アプリを完全に終了して開き直す（ページの再読み込みでは不可）。そうしてはじめてクライアントのモジュール表がこの bundle を認識する。

3. **設定**——設定 → dsh-switchman、またはホームサイドバーの「Switchman ディスパッチセンター」。設定は1ページだけ。見た目はこうで、上から下へ一度なぞれば終わり：

   ![dsh-switchman 設定ページの全体：インターフェース言語、言語設定、6つのディスパッチプール、能力順位と実行モード、チームのトグル、コンテキスト水位とコマンド](docs/assets/conf-interface-ja.png)

   - **インターフェース**——プラグイン自身の UI 言語。図のドロップダウンは「日本語」——切り替えのライブプレビュー。出荷時の既定は「自動」（DSH アプリの言語に追従）。言語を選べばその場でページ全体が切り替わり、保存後に記憶、いつでも「自動」に戻せる。
   - **言語**——エージェントの成果物の言語。図のスコープは「グローバル（この profile）」（プロジェクト単位も可、それぞれ `.switchman/lang.json` を読む）。返信 / コードコメント / ドキュメントの3つのドロップダウンは図ではすべて日本語で、各項目は「原語名（タグ）」表示——例えば「日本語 (ja)」。下には「現在：…」の状態行が付く。全部未設定でもよい——初回使用時に一度尋ね、覚えたらそれを使う。
   - **ディスパッチプール**——六枚のカードが三列二段（上段 economy・mechanical・main、下段 hard・vision・review）。カードはプロバイダーごとに候補モデルにチェックを付ける。「手動順」にチェックすると番号付きの優先リストになり、↑ ↓ × で並べ替える。各ルートには思考強度をピン留めできる（既定「レーンに追従」）。最上部の集計行はリアルタイムに更新され、図では「4/6 プール構成済み ・ 順位 2 件 ・ モード アドバイス」。
   - **能力順位 + 実行モード**——6プールの選択モデルの和集合を能力順に並べ、最強を先頭に（図では glm-5.3 を S、glm-5.3-flash を A に錨付き）。並べ替え・削減は自由。実行モードはアドバイス / 強制（強制＝プール外のモデルを即拒否）。
   - **エージェントチーム**——チームモードとホワイトリスト同期の2つのトグル。既定は両方オフ。図ではオンで、トグルの下に同期状態行がある。
   - **コンテキスト水位**——3段の閾値（図で 80000 / 120000 / 150000）、1回の読み取り予算（3000）、hard 段の挙動（絞って通す / ブロック）、自動引き継ぎトグル、サブエージェントの独立上限——すべてこの領域にある。最下部のコマンド行：`/ctx-pause` 介入を一時停止 ・ `/ctx-resume` 再開 ・ `/ctx-handover` すぐ引き継ぎ（セッションをアイドル境界まで導いてから圧縮するため、結果には数分かかることがある）。
   - **意図認識**——マスタートグル、分類器用小型モデルルート、分類器タイプ（auto / decision / chat）、独立候補リスト（各項目に一行の能力説明）、キャッシュウィンドウ / 信頼度しきい値 / 分類タイムアウト / 履歴予算、任意のフォールバックモデル。有効にするとモデルセレクターに「自動（意図認識）」エントリが現れ、入力欄の上に現在のルーティング先モデルと信頼度の chip が表示される。

4. **確認**——セッションヘッダーに ⚡「自律チーム」バッジ（隣の ◇ に現在セッションのモデル）。あるいはモデルに「あなたのシステムプロンプトの最終段落の見出しは何か」と尋ねる——答えに dsh-switchman の規程が出てくれば正しい。

**db-query の初回初期化**（スクリプトの依存はスキルディレクトリ内に置かれ、プロジェクトを汚さない）：

```bash
bash <インストールディレクトリ>/skills/db-query/scripts/setup.sh
```

**分類モデルの選び方**：決定モデルをローカルで動かすなら、Ollama で `tev1:4b-mxfp8` を実行するのがおすすめだ。分類器タイプは「判定エンドポイント（systemone）」を選び、エンドポイントに `http://127.0.0.1:11434/v1/systemone`、モデル名に `tev1:4b-mxfp8` を入力する。LLM カタログの chat 分類器にするなら、クラウドの小型モデルか、思考（推論）機能を持たないローカル小型モデルがおすすめだ——思考をオフにすれば、レイテンシと分類タイムアウトの失敗率を同時に抑えられる。

## デフォルト設定

以下は新規インストール直後の全デフォルト値（権威ソース：`host/config.js` の zod スキーマ）。

**インターフェースと言語**：`uiLocale` = `auto`（DSH アプリの言語に追従）、`langScope` = `global`、`langConversation/Comments/Docs` = 空（初回のセッションで一度尋ねて記憶。コメントとドキュメントの言語は会話の言語に追従）。

**ディスパッチプール**：6本のレーン（economy/mechanical/main/hard/vision/review）の候補はすべて空（＝システム既定のモデルを使い、介入しない）。手動順と effort のピン留めはすべてオフ/空。`dispatchEnforce` = `advice`（アドバイスのみで強制はしない）。

**コンテキスト水位**：soft `80000` / hard `95000` / force `150000` トークン。1回の読み取り予算 `3000`。予算超過時の挙動 `cap`（切り詰め＋警告）。`wmAutoHandover` = オン（force 段で引き継ぎドキュメント作成＋圧縮を自動実行）。サブエージェントのハード上限 = オン（150k を共有）。

**Agent Teams**：`teamsMode` = オフ。`syncWhitelist` = オフ（両者は互いに独立）。

**意図認識**（既定では利用不可。分類器＋候補最低1つ＋マスタートグルのオンが必要）：`intentEnabled` = オフ（オフの間は Auto エントリが隠れ、Auto を選んでいたセッションはフォールバックチェーンへ流れる）。分類器ルートは未設定。分類器タイプは `chat`。候補リストは空（プリセット分類はモデルを埋めないとルーティングに参加しない）。キャッシュウィンドウ `300` 秒 / 切替信頼度 `80` / 分類タイムアウト `60000` ms。履歴 `6` 件 / `2400` 文字。`intentContextWindow` = `200000`。

**コンテキストトリム**：`trimEnabled` = オン；`trimMode` = `auto`（完全自動）；成長ゲート `22500` + インクリメント `50000` トークン；圧力 `60%` / 緊急 `95%`；保護テール `6` 件；fold ペース上限は毎時 `6` 回；サイドモデルは未設定（セッションモデルを継承）——詳細は下の「自動コンテキストトリム」節で。

**初期状態のポイント**：① 意図認識が既定で使えないのは意図的な設計で、有効化は3ステップ（分類器、候補、トグル）。② Auto の実効ウィンドウは既定で 200000——ガードレールにより 0.8×ウィンドウ ≥ force 段（150000）が保証され、コア圧縮線（160000）は常にスムーズ引き継ぎ線（150000）より後ろにある。③ 既定でいちばん体感できるのは水位の3点セット：80k で委譲を促し、95k で読み取りを収束させ、150k で自動引き継ぎ（文書作成＋圧縮）。設定は一切不要。

## 自動コンテキストトリム

長いセッションを安く保つ：消化済みの会話レンジはコンパクトな決定論的サマリへ fold される——完全自動で、プロバイダのプロンプトキャッシュも壊さない。アイドル境界でトリムエンジン（`host/context-trim/`）が fold する価値のあるレンジを選び、サイドモデルがサマリを書き（緊急圧力時のみ、サイドモデル呼び出しなしの機械 fold に切り替わる）、fold をセッションの fold 状態へコミットする。以降のアウトバウンドリクエストはすべてその状態から再構築される——サマリブロックが fold 済みレンジを置き換え、ライブテールはそのまま。保存されたセッションは決して書き換えられず、ストリーム途中で何かが起きることもない。

自動化レベル（`trimMode`）：

- **`off`**——計測のみ：使用量とキャッシュヒットのサンプリングは動作；バナーなし、fold なし。
- **`advisory`**——セッションモデルが自ら fold する：`ctx_trim_fold` と `ctx_trim_status` のツールとプロトコルヘッドを公開。
- **`auto`**（既定）——advisory のすべてに加え、アイドル境界での自動 fold が3段階で動く：成長ゲート（前回の折り返し後の低点から測定した成長 > `trimGrowthTokens`——高位で折り返してもゲートが有効であり続けるためのアンカー——かつ連続圧縮可能インクリメントが `trimIncrementTokens` 以上）、圧力段（コンテキストウィンドウの `trimPressurePercent`）、緊急段（`trimEmergencyPercent`——独自クールダウン付きの機械 fold）。

すべてのキーは「設定 → dsh-switchman」にあり、既定値は `host/config.js` 由来：

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `trimEnabled` | `true` | マスタースイッチ。OFF で fold とメトリクスを完全停止（リスナーは純パススルーに退化）。 |
| `trimMode` | `auto` | `off` 計測のみ / `advisory` モデル駆動 fold / `auto` システム駆動 fold。 |
| `trimGrowthTokens` | `22500` | 成長ゲート：前回の fold 以降にアウトバウンド view がこれだけ増えたら fold。 |
| `trimIncrementTokens` | `50000` | ゲートの同伴条件：連続圧縮可能インクリメントもこの規模に達する必要あり。 |
| `trimPressurePercent` | `60` | 圧力段：view 使用量がコンテキストウィンドウのこの割合に達したら fold。 |
| `trimEmergencyPercent` | `95` | 緊急段：この割合で機械 fold を強制（サイドモデル呼び出しなし）。 |
| `trimWindowTokens` | `0` | ティア計算の実効ウィンドウ上限：min(モデルウィンドウ, 上限) で計算。`0` = `wmForceTokens` に追従。 |
| `trimProtectedTail` | `6` | 最後の N メッセージは決して fold されない。 |
| `trimMaxFoldsPerHour` | `6` | ローリング1時間あたりのサイドモデル fold ペース上限（緊急段は対象外）。 |
| `trimSideModel` | 未設定 | サマリを書くサイドモデルのルート。空欄 = セッションの現在モデルを継承。 |
| `trimStateDir` | 未設定 | fold 状態ディレクトリの上書き。空欄 = `<dshHome>/.dsh-switchman/state/trim/`。 |
| `surfaceFold` | `true` | コミット済みの fold をセッション表面へ出荷します（shadow-price 計量イベント + `surfaceOp` replace イベントのペア）。OFF はスプライスのみの view を維持。 |

**トリガーパス。** 段階チェックはアイドル境界で走り、アイドル状態イベントが届かないホストへのフォールバックとして、各モデルストリーム完了後にも走る（セッションごとに 60 秒につき 1 回の評価へスロットル）。すべての決定——fold も no-op も同様に——は、fold 状態ディレクトリ（`trimStateDir` を参照）内の `decisions.log` へ タイムスタンプ付きの 1 行の `key=value` として追記され、fold にオフラインの監査証跡を与える；行の語彙（`view-applied`、fold の決定/結果行、`surface-replace`、`surface-replace skipped reason=…`）は [docs/context-trim.md](./docs/context-trim.md) に一覧化されています。

**回線の真実と定常状態。** 決定行は `view=<n>` を持ち、応答が着地した後は `wire=<n>` も持つ——実際のプロバイダプロンプト（非キャッシュ入力 + キャッシュ読み取り + キャッシュ書き込み、ストリームの usage イベントからサンプリング）である。view の推定はメッセージ配列だけを数えるため、固定オーバーヘッド（実測 ≈ 17.3k：システムプロンプト + ツールスキーマ + persona）の分だけ常に回線より小さく読める。したがって圧力段と緊急段は `max(view, wire)` で評価し、プロンプトサイズの計測となるのは `wire` だけである。150k ウィンドウでは、健全なノコギリ波は fold 直後に回線 ≈ 40k ↔ 次の fold で 88–90k（ウィンドウの ≈27%–60%）を往復し、生の成長 ~50k ごとに fold 1 回、天井はウィンドウではなく圧力段によって 90k 付近に固定される。`surface-replace` 行が一度も現れないのに `view` が上昇する場合は、スキップ行（`incomplete-seqs`, `no-service`, `compaction-lock`）を読む。

**ホスト圧縮エポック。** fold の参照はメッセージ id と内容ハッシュにアンカーされるため、ホスト側の圧縮が再送履歴を置き換えると帳簿全体が一度に老化します。すべてのブロックが位置を特定できなくなり、view は元の履歴へ静かにフォールバックし（fail-open —— 決定ログには `view-applied applied=0` が記録されます）、プラグインは次のリクエストで成長ベースラインを圧縮後のビューに再アンカーします。ホスト圧縮は最後のバックストップとなるトリム層であり、プラグインの fold は単一ホストエポック内のきめ細かい作業を担います。 一部のディスパッチは、完全に凍結されたリクエスト配列やオプションオブジェクトを渡されます（現在のエージェントループは組み立て済みリクエストをディープフリーズします）。そのようなディスパッチについて、`injectView` は結果を決定ログに報告します：`nothing-to-apply`（位置特定できた fold ブロックがない——生履歴こそが view）、`in-place`/`swapped`（fold 済み view は出荷済み）、または `none`（fold は存在したが凍結されたディスパッチでは運べなかった——回線には生履歴が流れる）。**Surface replace は利用可能なときの出荷経路です**（`surfaceFold`、デフォルトで有効）：直列の `agent/turn-stopping` 境界にアイドルスイープを加えた時点で、プラグインはホスト式の shadow-price 計量イベントと、`surfaceOp {op:'replace', startSeq, endSeq}` を運ぶ 1 件の `user/message` 置換イベントを追記します。`sourceEventSeqs` は影となる表面ノードをすべてカバーします——ホスト自身の圧縮と同じ機構なので、コミット済みの fold はソース層から回線へ届き、凍結ディスパッチも例外ではありません。セッションの最近のディスパッチが `none` を記録している間、プラグインは view を計測専用と扱います：水位は代わりにプロバイダ報告の集計を測り（force 段階と自動引き継ぎは働き続け）、fold サイクルはサマライザ呼び出しを空焼きせず一時停止し、トリムバナーは当該行に `wire=raw`（folds not shipping; watermark reads the tally）の印を付けます。surface 機構を持たないホスト（またはフラグが off の場合）は、まさにこの従来動作を保ちます。

**fold がキャッシュヒットを守る仕組み。** fold は毎回プレフィックスを一度払い戻す。目指すのは償却コストであり、満点のヒット率ではない。エンジンはキャッシュ契約を守る：fold は追記専用——frontier は前進するだけで、凍結ゾーンは二度と編集されない。view は（履歴, fold 状態）から決定論的に再構築されるため、fold 間でシリアライズ済みプレフィックスはバイト同一のまま立ち、プロバイダキャッシュはヒットを続ける。fold 境界が assistant の tool-call をその tool 結果から切り離すことは決してなく、最後の `trimProtectedTail` メッセージは免除、そしてすべてが fail-open——内部エラーはパススルーに退化し、壊れたリクエストは生まれない。

**コンパクション仲裁。** 同じ履歴を巡る2つの自動トリマーは互いに二重要約し合い、frontier を破壊し合う。そこで `cordis.patch.yml` はホストの `dsh-compaction-basic` 行に `auto: false` を設定：context-trim が唯一のセマンティックトリマーになる。手動 `/compact` はそのまま使え、force 段の引き継ぎ（同じ手動パスを借用している）も無傷。オーバーフロー回復はトリムに移る：ウィンドウ超過の試行は一度失敗し、その後緊急段が view を fold して次の試行が収まる。

**fork 継承。** fork されたセッション（サブエージェント fork）は copy-on-fork で親の fold 状態を継承——ただし親の状態が存在し、子の履歴が実際に親の frontier を解決する場合のみ。さもなければ子はクリーンに開始する。子ごとに継承は一度きりで、再起動を跨いで冪等。

**水位は view を読む。** 水位バナーは保存側の集計ではなくアウトバウンド view のトークン数（fold 後にモデルが実際に見るもの）を報告するので、fold が進んだセッションが水位を hard 段に釘付けにすることはもうない。

## 仕組み

- ホスト側（`index.js` + `host/`）がバイト単位で不変のシステムプロンプト段（言語 / レーン / 水位プロトコル / チーム）と、末尾 runtime-context スナップショット経由で届くリアルタイム水位線（追記のみでプロンプト先頭を書き換えないため、プロバイダーの prompt cache は影響を受けない）、読み取り予算と enforce の二重ゲート、4つのスラッシュコマンド（ctx 3点セット + `/vision`）を注入する。保存した設定は次のターンのプロンプト組み立てで即効き、再起動は不要。
- クライアント側（`client.js`）は設定ページ、セッションヘッダーの ⚡ バッジと ◇ モデル表示、引き継ぎ中のライブ表示を描画する。設定スナップショットは Host のルートファミリー経由で読み書きする。
- ホームサイドバーの「Switchman ディスパッチセンター」入口は、ワンクリックで同じ設定ページを中央パネルで開く。元の設定入口は残る。
- `cordis.patch.yml` は出荷プリセットのプラグイン一覧を完全に保ち、persona suffix だけを拡張する。Agent Teams ツール本体は出荷バンドル由来で、チームモードをONにすると自動で有効になる。

## メンテナンスの注意

- DSH のアップグレードで出荷プリセットのプラグイン一覧が変わったら、新しい `presets/*.patch.yml` から `cordis.patch.yml` を再同期（doctrine suffix と、`compaction-basic` 行への `auto: false` によるコンパクション仲裁も保持）し、入れ直す。
- プロトコル行（`[SWITCHMAN:LANG|POOLS|WATERMARK|TEAMS]`）は意図的に英語のままバイト安定——ローカライズしない。
- `npm pack --dry-run` は監査済みの 60 ファイル / ~380 kB の形状を保つこと（展開後 ~1.26 MB、`docs/` は含まれない）。
